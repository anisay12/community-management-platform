# Lot L3 — Communities (bilingual EN/FR) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use beads-superpowers:subagent-driven-development (parallel batch mode) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Employees can browse a filterable catalogue of communities, open a community page, join / request / accept invitations / leave according to the community's access mode, and community leads and functional administrators can create, configure and run communities (settings, members and roles, requests, invitations, suspension, archiving), with every privileged action audited and the visibility rules of framing § 4.4 enforced and tested.

**Architecture:** New Django app `communities` (models, `selectors.py` with `Community.objects.visible_to(user)`, `policies.py`, `services.py`, thin views, templates on the L2 design system). New minimal app `notifications` exposing `notify()` (in-app rows only; L8 adds the bell, preferences and e-mails). Markdown fields rendered server-side with `markdown-it-py` and sanitized with `nh3` in `core/markdown.py`. Audit events gain a real `community` foreign key.

**Tech Stack:** Django 5.2 LTS, Python 3.13, PostgreSQL 16 (full-text `SearchVectorField` + GIN index), `markdown-it-py`, `nh3`, Bootstrap 5.3 components from L2, pytest + pytest-django, Playwright/axe (existing `a11y` suite).

**Source spec:** `.internal/specs/2026-10-09-mvp-knowledge-design.md` § 6 "Work package L3 — Communities"; framing § 4.3 (community roles), § 4.4 (permission matrix), § 6 table row `Community`, L3 row (acceptance: "Matrix § 4.4 tested; a private community never appears in a result for a non-member").

## Decisions taken in this plan (defaults)

- **Initial categories.** The original prompt's list of 12 categories is not in the repository. The data migration seeds 12 neutral, editable categories: Data & AI; Cloud & DevOps; Cybersecurity; Software engineering; Architecture; Product & UX; Agile & project management; Business consulting; Finance & risk; Telecoms & networks; CSR & sustainability; Life at Talan. Functional admins edit them from the UI; a later data migration can replace them if the owner supplies the official list.
- **Cover image** upload is deferred to L5 (needs the antivirus pipeline and private file serving, same as avatars in L1); the field exists, the UI shows a coloured header with the category icon.
- **Community page tabs.** Only tabs whose content exists are shown: About and Members. Feed (L4), Resources (L5), Lessons learned (L6) and Events (L7) register their tab when they ship (same "no fake empty screen" rule as the L2 navigation). The tab list is a small registry in `communities/tabs.py`.
- **Notifications.** `notifications.notify()` stores in-app rows only; there is no UI before L8.
- **Navigation.** A "Communities" entry is registered in the L2 navigation registry for every authenticated active user.

## Shared contracts (every task uses these names verbatim)

- App label `communities`; URL namespace `communities`, mounted at `/communities/`. Functional-admin category pages live under the existing `manage` namespace at `/manage/categories/`.
- Models (all with `created_at`/`updated_at` UTC, `public_id` UUID where an object appears in a URL):
  - `CommunityCategory(name unique, slug unique, description, icon (Bootstrap Icons name, default "people"), order int, is_active bool)`; ordering `order, name`.
  - `Community(public_id, name, slug unique, category FK PROTECT, tagline ≤160, description, rules, objectives (Markdown text), cover_image (FileField, optional, unused UI), access_mode ∈ AccessMode{OPEN="open", REQUEST="request", INVITE="invite"}, listed bool default False, allow_member_uploads bool default False, require_post_review bool default False, status ∈ Status{ACTIVE="active", SUSPENDED="suspended", ARCHIVED="archived"}, archived_at null, created_by FK user SET_NULL null, tags M2M taxonomy.Tag blank, search_vector SearchVectorField null, member_count PositiveInteger default 0, last_activity_at)`; partial unique constraint on `Lower(name)` where status ≠ archived (`community_name_unique_active`); GIN index on `search_vector`; indexes on `category`, `access_mode`. `search_vector` is refreshed by the services (name weight A, tagline B, description C) — no trigger.
  - `CommunityMembership(community FK CASCADE, user FK CASCADE, role ∈ Role{MEMBER="member", CONTRIBUTOR="contributor", EXPERT="expert", MODERATOR="moderator", ANIMATOR="animator", OWNER="owner"}, joined_at, notification_level ∈ {"all","highlights","none"} default "highlights")`; unique (`community`,`user`); index (`user`,`community`), (`community`,`role`). Role order for comparisons: `ROLE_RANK = {member:1, contributor:2, expert:3, moderator:4, animator:5, owner:6}` in `communities/roles.py` with `role_at_least(role, minimum) -> bool`. Labels EN/FR: Member/Membre, Contributor/Contributeur, Expert/Expert, Moderator/Modérateur, Facilitator/Animateur (code `animator`), Lead/Responsable (code `owner`).
  - `MembershipRequest(public_id, community, user, message ≤500, status ∈ {pending, accepted, rejected, cancelled}, decided_by FK null, decided_at null, decision_note blank)`; partial unique (`community`,`user`) where status = pending (`one_pending_request`).
  - `CommunityInvitation(public_id, community, invited_user, invited_by, role (≤ animator), status ∈ {pending, accepted, declined, revoked, expired}, expires_at = now + 14 days)`; partial unique (`community`,`invited_user`) where status = pending.
  - `CommunityCreationRequest(public_id, requester, name, category FK PROTECT, justification, status ∈ {pending, approved, rejected}, decided_by, decided_at, decision_note, community FK null (set on approval))`.
  - `AdminAccessGrant(community, user, reason (min 10 chars), created_at, expires_at = now + 1 hour)` — "Access as administrator" for functional admins (audited).
  - `notifications.Notification(recipient FK CASCADE, category CharField(64), actor FK SET_NULL null, target_type, target_id, community FK null SET_NULL, read_at null, created_at)`; index (`recipient`, `read_at`, `-created_at`).
  - `audit.AuditEvent.community_id` (BigInteger) becomes `community = ForeignKey("communities.Community", null, blank, SET_NULL, db_constraint=True, related_name="+")` keeping the same DB column `community_id` (migration with `AlterField`/state operations so existing rows survive); `audit.services.record(..., community=None)` accepts a `Community` (keep the `community_id=` kwarg working for existing callers).
- Errors: `core.errors.DomainError(code, message)` with codes `last_owner`, `invite_only`, `already_member`, `not_member`, `request_pending`, `forbidden_role`, `read_only` (suspended/archived), `name_taken`, `invalid_state`, `expired`.
- Policies (`communities/policies.py`, all `-> bool`, never raise): `can_view_metadata(user, community)`, `can_view_content(user, community)`, `can_join(user, community)`, `can_manage_members(user, community)` (animator+ or functional admin), `can_change_roles(user, community)` (owner or functional admin), `can_configure(user, community)` (owner or functional admin), `can_suspend(user, community)` (functional admin), `can_archive(user, community)` (owner of it or functional admin), `can_create_community(user)` (`community_creator` role or functional admin or superuser), `can_manage_categories(user)` (functional admin or superuser), `membership_of(user, community) -> CommunityMembership | None` (memoised per request on the user object like `accounts.roles`).
- Visibility (`CommunityQuerySet.visible_to(user)`): active employees see `open` and `request` communities that are active or suspended, plus `invite` communities where they are members or which are `listed`; archived communities only for their members and functional admins; functional admins see the metadata of all. `can_view_content`: open → any active employee; request/invite → members; functional admin → only with a valid `AdminAccessGrant`. Not visible → 404; visible but forbidden action → 403.
- Services (`communities/services.py`, `@transaction.atomic`, actor first, audited with `audit.services.record(action=..., community=...)`, `notify()` via `transaction.on_commit`): `create_community(*, actor, name, category, tagline, description="", rules="", objectives="", access_mode, listed=False, tags=()) -> Community` (creator becomes owner, member_count 1; audit `community.created`), `update_settings(*, actor, community, **fields)` (`community.updated`, `changes` before/after), `join(*, actor, community, message="") -> CommunityMembership | MembershipRequest` (open → membership `community.joined`; request → pending request, idempotent, `community.membership_requested`; invite → `invite_only`), `cancel_request`, `accept_request(*, actor, request)` / `reject_request(*, actor, request, note="")` (`community.request_accepted/rejected`, notify requester), `invite(*, actor, community, user, role="member")` (role ≥ animator only by owner → `forbidden_role`; `community.invited`; notify invitee), `accept_invitation` / `decline_invitation` (invitee only; expired → `expired`), `revoke_invitation`, `leave(*, actor, community)` (`last_owner`; `community.left`), `remove_member(*, actor, membership)`, `change_role(*, actor, membership, role)` (`last_owner` when demoting the last owner; `community.role_changed` with before/after), `suspend` / `reactivate` / `archive` / `unarchive` (`community.suspended` …), `request_creation(*, actor, name, category, justification)`, `approve_creation_request` / `reject_creation_request` (functional admin; approval calls `create_community` with the requester as owner), `grant_admin_access(*, actor, community, reason) -> AdminAccessGrant` (`community.admin_access`), category services `create_category` / `update_category` / `deactivate_category` (`category.*`). Every membership change updates `member_count` with `F()` in the same transaction. Suspended or archived communities reject membership changes other than by functional admins (`read_only`).
- `notifications.services.notify(category: str, recipients: Iterable[User], *, actor=None, target=None, community=None) -> None`: registers `transaction.on_commit` that `bulk_create`s one row per distinct active recipient, skipping the actor. Categories used in L3: `community.request_accepted`, `community.request_rejected`, `community.invited`, `community.request_received` (to animators+), `community.creation_decided`.
- Markdown: `core.markdown.render(text: str) -> str` (markdown-it-py "commonmark" + tables, no raw HTML; nh3 sanitization with tags limited to headings, p, lists, a, code, pre, blockquote, table family, em/strong, hr, br; link schemes https/http/mailto; `rel="noopener noreferrer nofollow"` on links; images stripped). Template filter `{{ text|markdown }}` in `core/templatetags/markdown_tags.py`.
- URL names (namespace `communities`): `catalogue` (`/communities/`), `create` (`/communities/new/`), `creation_request` (`/communities/request/`), `my_invitations` (`/communities/invitations/`), `detail` (`/communities/<slug>/`), `members` (`/communities/<slug>/members/`), `join`, `leave`, `cancel_request` (POST-only, `/communities/<slug>/join/` …), `invitation_respond` (`/communities/invitations/<uuid:public_id>/respond/`, POST), `admin_access` (`/communities/<slug>/admin-access/`), and management under `/communities/<slug>/manage/`: `manage_settings`, `manage_members`, `manage_member_role` (POST), `manage_member_remove` (POST), `manage_requests`, `manage_request_decide` (POST), `manage_invitations`, `manage_invitation_revoke` (POST), `manage_status` (POST: suspend/reactivate/archive/unarchive). Functional-admin pages in namespace `manage`: `category_list`, `category_create`, `category_edit`, `creation_request_list`, `creation_request_decide` (POST).
- Templates under `src/communities/templates/communities/` extending `base.html`, using L2 components (`components/community_card.html`, `card`, `tabs`, `breadcrumb`, `pagination`, `form_field`, `form_errors`, `empty_state`, `role_badge`, `modal`, `alert`). Community role badges use a new `components/community_role_badge.html` (Task 2 owns it).
- Global constraints of the previous plans still apply (English code/docs, bilingual UI with a complete French catalogue, 404 vs 403, no modifying GET, CSRF, `make lint`/`make test` ≥ 85 %/`make i18n-check`/`make assets-check`/`make test-a11y`, commit trailers `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_011UFaooKLLSUGTLxQZfHT7p`).
- Parallel tasks each edit `src/locale/fr/LC_MESSAGES/django.po`; that is expected: the orchestrator merges catalogues with `msgcat` and re-runs `makemessages`. Each task still leaves its own catalogue complete.
